# 关键词 PIR（匿踪查询）

> 状态：**已实现**（核心库、C ABI、Python）。OPRF + 分桶下发，支持 Ristretto255、P-256、SM2、FourQ。数据库支持追加、更新、删除，标签长度任意。半诚实安全，泄露所查的桶（不是严格的 PIR）。记录加密的 IV 固定为 0，更新会泄露新旧标签的异或，见「安全性」。

## 概述

服务端持有一个“键 → 标签”数据库（如手机号 → 用户信息），客户端用一批关键词查询，得到命中关键词的标签：

- 服务端不知道客户端查了哪些关键词，只知道它们落在哪些桶。每个关键词藏在所在桶的约 `bucket_size` 个键中。
- 客户端只能解密自己查询的关键词对应的记录。

适合大库（千万到亿级）、标签几百字节、一次查一批的场景。数据库离线写入，之后可以随时增删改；在线只做 OPRF 和读盘。

**和 OPRF-PSI 的区别**：OPRF-PSI 每次会话换密钥、发送方重算全部元素，只回答“在不在”。PIR 用长期密钥加密整个库，回答“对应的标签是什么”，在线只下发被查到的桶。

**通信量是选型的关键**：客户端下载每个命中桶的全部记录。$q$ 个关键词、$B$ 个桶时，命中约 $B(1 - e^{-q/B})$ 个桶，$q$ 接近或超过 $B$ 时几乎要下载整个库。例如 1 亿条、每条约 320 字节、每桶约 1024 条：查 1000 个关键词约下载 0.3 GiB；查 100 万个几乎下载全部 30 GiB（估算）。批量很大时应增大 `bucket_size`，或改用 PSI（不带标签）。

## 协议

### 记录

服务端从 32 字节种子派生长期 OPRF 密钥 $k$。每条记录 $(x, \ell)$ 存成：

$$
\mathrm{id} = F_k(x)[0..16],\qquad
\mathrm{body} = \mathrm{CTR}_{F_k(x)[16..32]}\big(\mathrm{IV} = 0,\ |\ell|\ (\text{u32 BE}) \,\|\, \ell\big)
$$

- $F_k$ 是与 OPRF-PSI 相同的 2HashDH OPRF（RFC 9497 OPRF 模式的形状，见 [psi-oprf.md](psi-oprf.md#协议)）。四个套件的 Finalize 输出都至少 32 字节，直接切成两半，不再做哈希。
- id 只由键和 $k$ 决定，所以写入方拿到键就能定位记录，库里不存明文键。
- 标签按真实长度存储。补齐只在下发时做，见「查询」。
- 桶：$2^j$ 个桶时，记录的桶号是 id 的高 $j$ 位。$j$ 不存储，服务时按当前记录数算出。

### 存储：段 + 清单

一个数据库是一个目录：

| 文件 | 内容 |
| --- | --- |
| `MANIFEST` | 曲线、密钥指纹、版本号（generation）、记录数、最长标签、元数据、当前生效的段列表；原子替换 |
| `seg-<n>.pir` | 段：按 id 严格递增的记录（记录或墓碑），带稀疏索引（每 64 条一项）；写好后不再修改 |
| `LOCK` | 写入方的文件锁：同一目录同时只能有一个写入方 |
| `work-<随机>/` | 未提交批次的临时文件，提交、回滚或下次打开时删除 |

- **写入**：`upsert` 和 `delete` 先计算 id 和密文，再按 id 首字节分到 256 个临时文件（含密文，不含明文）。批次再大也不必放进内存。
- **提交**：`commit` 逐个分区排序，写出一个新段。同一批次里，对同一个键的最后一次操作生效。写完后更新清单，生成新版本号。
- **覆盖规则**：新段覆盖旧段里相同 id 的记录，墓碑表示删除。
- **合并**：`compact` 把所有段多路归并成一个，丢掉墓碑和被覆盖的旧版本，并修正记录数和最长标签。之后删除旧段。

段的二进制格式见 `core/src/algorithms/pir/segment.rs`，清单格式见 `db.rs` 的模块注释。

### 查询

```
客户端（关键词 x_1..x_n）                          服务端（某个快照，k）
           ◀── params：曲线、桶数 2^j、记录数、补齐长度、版本号、元数据 ──
去重、打乱；r ← 随机标量；q_i = H(x_i)^r
           ── query：版本号，[q_i] ──▶
                                                    e_i = q_i^k
           ◀── eval：[e_i] ──
F_k(x_i) = Fin(x_i, e_i^(1/r)) → (id_i, 密钥_i)
           ── fetch：版本号，{ id_i 的高 j 位 }（升序）──▶
                                                    各段中这些桶的记录 → 取最新版本、去掉墓碑
                                                    → 桶内随机打乱 → 补齐
           ◀── chunk … chunk(last)：每条 id ‖ 长度 ‖ body ‖ 随机字节 ──
按 id 查表，命中则解密（读长度前缀，忽略补齐的字节）
```

- 两来两回：客户端要先拿到 $F_k(x_i)$，才知道 id，进而知道桶号。
- 服务端为每个会话固定一个快照（版本号）。查询期间有新的提交或合并，这个会话也不受影响。`reload` 之后，新会话使用新快照，带旧版本号的消息会被拒绝。
- 段文件按 id 排序。下发前在桶内随机打乱，客户端从顺序上看不出未查询记录的 id 排名。
- 服务端校验客户端的点（在曲线上、在素数阶子群内、不是单位元），以及桶号严格递增、小于桶数、个数不超过关键词数。`max_keywords` 可以在计算之前拒绝过大的查询。

### 补齐（服务端设置）

| `padding` | 下发的 body 长度 | 客户端看到的 |
| --- | --- | --- |
| `MAX`（默认） | 统一补到 4 + 自上次合并以来的最长标签 | 只有一个全库上限 |
| `NONE` | 真实长度 | 所下载的每条记录的标签长度 |

补的是随机字节，和 CTR 密文分不出来。补齐长度只影响下发，改了不需要重写数据。注意：`MAX` 的上限只增不减，删掉最长的那条标签之后，要合并一次才会变小。

### 消息格式

整数大端，点用各曲线的压缩编码：

| 消息 | 格式 |
| --- | --- |
| params | `0x31 ‖ version=2 (u8) ‖ curve (u8) ‖ j (u8) ‖ records (u64) ‖ padded_len (u32) ‖ generation (u64) ‖ metadata_len (u32) ‖ metadata` |
| query | `0x32 ‖ generation (u64) ‖ n (u64) ‖ q_1 … q_n` |
| eval | `0x33 ‖ n (u64) ‖ e_1 … e_n` |
| fetch | `0x35 ‖ generation (u64) ‖ k (u64) ‖ b_1 … b_k (u32)` |
| chunk | `0x34 ‖ last (u8) ‖ count (u64) ‖ count × (id (16) ‖ len (u32) ‖ body (len))` |

## 参数

| 曲线 | OPRF 套件 | 哈希（密钥派生、桶以外的用途） | 记录加密 |
| --- | --- | --- | --- |
| Ristretto255 | `ristretto255-SHA512` | SHA-256 | AES-128-CTR |
| P-256 | `P256-SHA256` | SHA-256 | AES-128-CTR |
| SM2 | `SM2-SM3`（自定义） | SM3 | SM4-CTR |
| FourQ | `FourQ-SHA256`（自定义） | SHA-256 | AES-128-CTR |

- 选 SM2 时全程只用 SM2、SM3、SM4。
- `bucket_size`（服务端设置，默认 1024）：桶数取 $2^j$，$j$ 是满足 $\lceil \text{记录数} / 2^j \rceil \le$ `bucket_size` 的最小值，所以每桶实际在 `bucket_size / 2` 到 `bucket_size` 之间。用 2 的幂是因为库变大时桶数翻倍，新旧两种桶数下的桶互相嵌套。同一个关键词在两种桶数下各查一次，范围最多缩小到较细的那个桶。
- 标签长度不设上限，只受记录和消息里 32 位长度字段的限制（约 4 GiB）。
- 关键词最长 65535 字节（OPRF 输入用 2 字节长度前缀），元数据最长 64 KiB，桶数最多 $2^{20}$。
- 大标签的代价：
  - `padding = MAX` 时，一条大标签会让所有记录都补到它的长度，下载量放大到 记录数 × 最长标签。
  - 服务端应答时，一次在内存里放一个桶，内存约为 桶内记录数 × 补齐后的长度。
  - chunk 在桶内按约 4 MiB 切分，超过 4 MiB 的单条记录独占一个 chunk。
  - 标签大小差别很大时，建议用 `padding = NONE`，或者标签里只放引用（如对象存储地址加解密密钥）。
- 服务端密钥：$k$ 由 ChaCha20 采样，种子为 $H(\texttt{"CRYPTEX-PIR-KEY-V1"} \,\|\, \text{套件 ID} \,\|\, \mathrm{seed})$。清单里存 $F_k$ 在固定输入上的前 16 字节，用来发现种子不对或派生方式有变化。各曲线的这个值都有固定测试。

## 性能

**理论开销**（$n$ 个不同关键词，命中 $s$ 个桶，$m$ 条记录，平均每条 $R$ 字节）：

| | 开销 |
| --- | --- |
| 写入 $w$ 条 | $w$ 次 hash-to-group + $w$ 次标量乘 + $w$ 次 CTR；提交时排序这 $w$ 条 |
| 合并 | 顺序读写全部段，不做群运算 |
| 客户端计算 | $n$ 次 hash-to-group + $2n$ 次标量乘 + 1 次求逆 + 收到记录的 id 查表 |
| 服务端在线计算 | $n$ 次点校验 + $n$ 次标量乘 + 读 $s$ 个桶（每段一次二分 + 一次连续读） |
| C → S | $n$ 个点 + $4s$ 字节 |
| S → C | $n$ 个点 + 约 $s \cdot (m/2^j) \cdot (20 + R)$ 字节 |

**实测**：Apple M5（10 核），`PIR_RECORDS=… PIR_CURVE=… cargo test --release pir_timing -- --ignored --nocapture`（`core/src/algorithms/pir/tests.rs`），全局线程池，同一进程内存中收发（不含网络）。键为 11 位数字，标签 300 字节，`bucket_size` = 1024，`padding` = `MAX`。

“增量”一栏是一次提交：新增 1%、更新 1%、删除 0.1%。

| 曲线 | 记录数 | 首次写入 | 增量（3.1%） | 合并 | 查询数 | 命中桶 | S → C | 双方计算 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Ristretto255 | 100 万 | 4.6 s | 0.11 s | 0.12 s | 1000 | 651 / 1024 | 198.2 MiB | 83 ms |
| Ristretto255 | 100 万 | | | | 1 万 | 1024 / 1024 | 311.8 MiB | 242 ms |
| SM2 | 100 万 | 20.2 s | 0.43 s | 0.13 s | 1000 | 631 / 1024 | 192.1 MiB | 119 ms |
| SM2 | 100 万 | | | | 1 万 | 1023 / 1024 | 311.5 MiB | 612 ms |
| Ristretto255 | 1000 万 | 48.2 s | 0.99 s | 2.6 s | 1000 | 970 / 16384 | 184.8 MiB | 152 ms |
| Ristretto255 | 1000 万 | | | | 1 万 | 7470 / 16384 | 1423.4 MiB | 1.12 s |

- **合并前查询**：两个段（合并前）时查 1000 个关键词，100 万条为 95 ms，1000 万条为 134 ms，与合并后相差不大。
- **内存和磁盘**：1000 万条时，进程峰值内存 0.70 GiB（`/usr/bin/time -l`），合并后数据库占 3.06 GiB。
- **合并很快的原因**：合并在页缓存里完成，是一次顺序归并，不涉及群运算。冷缓存、机械盘的情况未实测。
- **在线时间以下载为主**：百兆网上 185 MiB 约 15 s（估算，未实测网络）。
- **1 亿条**：首次写入约 8 分钟（Ristretto255）、合并约 30 s，都是线性外推的估算，未实测。

## 安全性

模型：半诚实。

**服务端知道**：
- 不同关键词的个数 $n$。
- 它们落在哪些桶。服务端有 $k$，能算出任何键的 id，因此知道每个关键词属于某个约 $m / 2^j$ 个键的集合。
- 查询时间。

多次查询同一个关键词会落在同一个桶，服务端可以把这些查询关联起来。关键词本身是隐藏的：盲化后的点在 DDH 假设下与随机点不可区分。

**客户端知道**：
- 快照的公开参数：记录数、桶数、补齐长度、元数据、版本号。
- 所下载各桶的记录数；`padding = NONE` 时还有每条标签的长度。
- 命中关键词的标签。

对于没查询的键，它只看到 id 和密文。不知道 $F_k$，这些就与随机值不可区分。2HashDH 在 One-More-Gap-DH 假设下保证：$n$ 次求值最多得到 $n$ 个 $F_k$ 值。

**增量带来的泄露**（已与需求方确认接受）：
- **看得出变化**：客户端在两个版本下载同一个桶，能看出哪些 id 新增、哪些消失、哪些的密文变了，不知道对应哪个键。
- **IV 固定为 0，更新会复用密钥流**：同一个键的新旧密文异或，等于 $(|\ell_{旧}| \,\|\, \ell_{旧}) \oplus (|\ell_{新}| \,\|\, \ell_{新})$，取两者较短的长度。后果是：
  - 曾查询过这个键的客户端，以后只要下载到这个桶，就能算出新标签，不必再查询这个键，也就绕过了服务端的查询次数限制。
  - 没查询过的客户端，也能得到新旧标签的异或。标签格式固定时，这会泄露大量信息。
  - 新旧两版密文同时存在于合并前的旧段和备份里，拿到这些文件的人（没有种子）也能算出这个异或。
- **删除不追溯**：客户端已经下载的密文，之后查到对应的键时仍能解开。
- **要彻底切断**：换种子，把数据全量重新写入一个新库。

如果将来要消除复用密钥流的问题，最小的改动是每条记录存一个 IV，取 $H(F_k(x)[16..32] \,\|\, \ell)$ 或者随机值，每条多 16 字节。这需要改段格式和 chunk 格式，没有实现。

**使用注意**：
- `seed` 是服务端的长期秘密。泄露后，任何拿到数据库或回复的人都能解密所有标签。不要和数据库目录放在一起。
- 长期密钥意味着查询次数没有上限。平台应限制每个客户端的查询量（`max_keywords`），并定期换种子重建。
- 临时目录 `work-*` 和段文件只含 id 和密文，不含明文键或标签。数据库目录仍然应该只有服务端能读。
- SM4 来自 `sm4` crate，S 盒用查表实现，不是常量时间（缓存时序）。
- 半诚实：恶意服务端可以返回错误的标签，客户端发现不了。
